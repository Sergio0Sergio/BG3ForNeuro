# BG3 Neuro SDK Integration — Wayfinder Map

## Destination

A complete architectural specification for integrating Baldur's Gate 3 with the Neuro SDK: modules, interfaces, state formats, action schemas for combat/dialogue/exploration, the IPC protocol, and testing. The result is a document ready to be handed to a contractor.

## Notes

- Language: C# as a separate process
- State extraction: BG3 Script Extender (Lua/C# mod)
- Action execution: BG3SE Lua script — full catalog: [research/bg3se-lua-action-api.md](research/bg3se-lua-action-api.md) (signatures, BG3SE single-threaded threading, reliability matrix; resolves the "Not yet specified" entry about action-in-turn/TurnOrder, path → native MoveTo, timeouts and errors 07)
- BG3SE ↔ C# communication: ~~Named pipe~~ → **file-based IPC (Ext.IO + JSON)** — research showed BG3SE has no native named pipe; file-based IPC is the primary path, named pipe (C# mod) is the upgrade path. Details: BG3SE IPC Protocol ticket
- State updates: event-driven
- Testing: Randy + unit tests + integration tests
- References: neuro-sdk/API/SPECIFICATION.md, neuro-sdk/API/BEST_PRACTICES.md
- **Map status: destination reached.** All 9 decision tickets resolved; only post-v1 experiments remain (see Out of scope). The final specification is assembled from tickets 01–09.

## Decisions so far

- [BG3SE IPC Protocol](issues/02-ipc-protocol.md): No native named pipe in BG3SE; LuaSocket and HTTP are unavailable. Primary path is file-based IPC via `Ext.IO.SaveFile`/`LoadFile` + JSON (`Ext.Json`), non-blocking polling via `Ext.Timer.WaitForRealtime`. C# process runs on separate threads. Named pipe (C# mod) — Phase 2 upgrade path. No ready-made BG3→Neuro integrations found.
- [Architecture Overview](issues/01-architecture-overview.md): Two-process architecture. BG3SE Mod (Lua) is dumb: `StateExtractor` + `ActionExecutor` + `IpcFileHandler`. C# Process carries all the logic: `NeuroWebSocketClient`, `IpcClient`, `StateSerializer`, `ActionRouter`, `DecisionLoop`. File-based IPC (JSON) in the solution, decision in C#. Entity aliases for Neuro. `controlledPartySize` 1..4 in the config. Force carries fresh markdown state (ephemeral), rare context for rules. Force policy (§1.6, review C): triggers — controlled character's turn / DialogStarted / leaving combat / timeout-then-force; priority always `low` (BG3 is turn-based); a new force cancels+replaces (spec) because it carries full state.
- [State Format](issues/03-state-format.md): Three state generators (combat/dialogue/exploration). Meters as distances. Hybrid distance + "in range/covers" per spell (single code path with validator). Dialogue numbers = order in the BG3 dialog window UI (1-based), matching streamer mode; `option_index` primary + `option_text` fallback. Awareness as a visibility filter (hidden/invisible not visible, no cheating). `toggle_mode` in exploration-state: `[normal]` (E6, X3 — no stealth in v1). Everything is exposed in `config.json` (combat/dialogue/exploration blocks with defaults). Don't write "You are Neuro" in the force header; only dynamics (controlled/mode/turn); rules — one-time startup context (silent).
- [Combat Action Schemas](issues/04-combat-actions.md): 8 combat actions: `move_to_target`, `attack_entity` (no weapon_slot, always main), `cast_spell` (target_id + coverage for AoE + position fallback), `use_item`, `throw` (→ `not_supported` in v1), `bonus_action` (full enum always, drink_potion inside), `set_reaction` (full enum), `end_turn`. Common `actor?: string` on all — executor alias, required when party > 1, omitted when party = 1. C4: dynamic registration only at the action level, never enum resize (BEST_PRACTICES: frequent schema changes slow down responses).
- [Dialog Action Schemas](issues/05-dialogue-actions.md): One action `select_dialogue_option` (`option_index` primary, `option_text` fallback; number = order in the BG3 dialog window UI). PERSISTENT registration at startup — no reg/dereg (fail when no dialogue). Context: title+line+options with hints. Forced dialogue: DecisionLoop switches mode, persistent registration stays. Trading — out of scope.
- [Exploration Action Schemas](issues/06-exploration-actions.md): 8 exploration actions: `move_to_entity`, `interact_with` (free-form `interaction_type`, validation in the plugin), `loot` (separate), `open_map`/`open_inventory` (view only + use_item/travel_to), `toggle_mode` (target_id? + mode; in v1 enum only `["normal"]`, `"stealth"` removed per X3 — no public API), `rest` (full/partial), `travel_to` (destination = region name (primary), region_id? optional for disambiguation; state gives [Name (id)]). Common `actor?: string` (analogous to combat). UI clicks inside map/inventory — out of scope.
- [Action Execution Layer](issues/07-action-execution.md): One in-flight action (BG3SE Lua single-threaded → serialization). File-based IPC: C# validates + writes `action_<id>.json`; Lua poll (100–250ms) → dispatch → `result_<id>.json` `{success, error_code, error_detail}`. ACK timeout 5s (ticket 08). Long actions: `running:true` → final via event (`CastedSpell`), we don't block the thread. Dialogue: X1 — `ClientAutoselectExecutor`: client Lua finds the element by option_index (= UI order), highlights and clicks it, the human presses nothing (confirm collapsed to an alias in `dialogue.mode`); client unavailable → fallback to `not_supported` + warning (Neuro never left without a channel). `throw` — in the schema as `not_supported` (honest failure). Stealth: X3 — in v1 `toggle_mode` only `"normal"`, remove `"stealth"` (no public API) until a solution appears. Player attacks: via `ServerCastRequest.OsirisCastRequests` (honest with AP), `Osi.Attack` — enemies/fallback. SpellId: normalization in StateExtractor, prototype names throughout the pipeline (`Ext.Stats.Get`). Full JSON-Schema of all 17 actions — specification §5.4.
- [Error Resilience](issues/08-error-resilience.md): R1 — reconnect: `startup` + re-registration, handling `actions/reregister_all` (persistent set). R2 — mod writes `heartbeat.json` every 2s, stale when older than 10s (tolerant to engine pauses, detection is not urgent — turn-based) → `mod_unavailable` + re-init. R3 — we always dispatch any Neuro action (force does not block); clarified (C): a new force cancels+replaces the active one (spec), safe because it carries full state. R4 — no disposables, everything persistent. R6 — two-phase response: success on validation, outcome via next state. R7 — game crash = full re-init via reconnect path. R8 — JSON garbage → log+skip; invalid action → failure with list of options. R9 (review D) — error_code vocabulary split into **two channels**: Channel A (action/result, validation): target_missing/not_in_combat/no_spell/no_camp/not_supported/invalid_parameters/target_not_in_range/wrong_phase(E7: bonus_action/set_reaction outside own turn)/dialogue_closed/mod_unavailable(before validation); Channel B (next state+context, execution): action_failed/mod_unavailable(during execution). We don't send late action/result — the server will discard it; the next force restores the picture (§1.6).
- [Testing Architecture](issues/09-testing-architecture.md): T1 — Randy as-is (`ws://localhost:8000` + HTTP POST `:1337`), no forking. T2 — unit: StateSerializer, ActionRouter, IpcClient (fake files), ConfigLoader, ErrorMapper + a separate range/AoE coverage module; Lua mod against `Ext.*` mocks — smoke on the bench, not in CI. T3 — integration: BG3SE mock files + C# pipeline in CI (A) and with Randy (B); real Neuro — manual regression. T4 — smoke: fake BG3SE in CI + mandatory manual run on a real game before release. T5 — automated tests on simulated states to the maximum extent + manual regression checklist (combat/dialogue/exploration, without trading).
