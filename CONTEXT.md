# CONTEXT.md

## Glossary

- **option_index** — the dialog reply index; equals the 1-based order of the button in the game's dialog window. Canonical identifier that Neuro sees in the state and by which the mod makes the selection.
- **option_text** — the reply text; a fallback for selection when the window numbering and the state have diverged.
- **Dialogue option selection** — the action "Neuro picks an option → the option actually gets selected in the game." Only runs on the client context; there is no server-side path.
- **Server context** — the main half of the mod: emitting game state and receiving commands from the app.
- **Client context** — the second half of the mod, runs in the game's client context and can see the UI; the only way to actually click on the interface (including dialogs).
- **Cross-OS message** — relaying the "select an option" command from the server context to the client context. In single-player it stays inside one process; in multiplayer it goes over the network.
- **Honest refusal** (X1) — the principle: if selecting an option is impossible (client unavailable, dialog closed), the mod explicitly answers `not_supported` plus a warning instead of staying silent, so Neuro never loses its feedback channel.
- **Emission** — the mod's outbound channel: the game state the mod writes outward (`bg3_to_neuro.json`) for the app/agent. The counterpart of command intake (`neuro_to_bg3.json`).
- **Perception** — what the party is aware of about an entity: it sees it, discovered it, or remembers it. One honest-perception principle: Neuro only receives what was perceived.
- **visible / known / unknown** — the entity perception three-state: `visible` — perceived right now; `known` — perceived before, not now (we remember its last location); `unknown` — never perceived, absent from the state.
- **last_seen** (last known) — the entity's position in the `known` state: a frozen coordinate from the moment of last perception, not the current true location.
- **Party** — the members of the player's party; always "known" and not subject to the perception filter.
- **Concentration** — the state of a caster maintaining a concentration spell (Bless, Guidance, etc.). The concentration indicator hangs on the **caster's** portrait, even when the status is applied to an ally.

## Diagnostic traps (bench truth)

- **The caster's concentration icon ≠ status location.** The visual "status at Shadowheart" when casting Bless/Guidance on an ally is the caster's concentration icon, not the status itself. The only sources of truth about the status bearer: raw `StatusManager` via `stats_probe` (`entityStatusDump`/`Statuses`), or the inventory of whoever's turn it currently is. `bg3_to_neuro.json`/`state_capture` read the same StatusMachine but do not expose hidden/internal statuses.
- In-range targeting of a single-target friendly-buff cast lands on the request's `targetUuid` for any flag combination (`force_flags` on/off × osiris/network queue). The observed "self-casts" (tickets 16/22) were an artifact of misreading the concentration icon.
- **Cast render artifacts are cosmetic, not signals (UX decision, ticket 22, 2026-09-21).** Visual effects at the caster (concentration icon, "projectile/beam from the caster") carry no information about the status bearer. The app/Neuro must rely on the state/status model rather than the game's portrait icons; fixing the render itself is not required. v0.8.61 control: `bless` cleric→Tav 4.6 m → raw `StatusManager` (`stats_probe`) after: `tav [RALLY, BLESS]`, `cleric [RALLY]`; action economy 1.0→0.0, L1 slot 1.0→0.0.
- **`throw` — unsupported: the engine rejects a synthetic throw in any queue (ticket 28, bench 2026-09-23, v0.8.79).** All six variants tested (force x4 queues `osiris/network/item/anubis` + honest `FromClient` x2 `item/network`) yield `CastSpellFailed(caster, "Throw_Throw", "throw", "", storyActionID=0)`; the `UsingSpell` event never fires even once. The request does land in the queue correctly and is structurally identical (opts/`a8=1`/`Item`) to successful honest attack casts in `OsirisCastRequests` — the engine rejects precisely the `ItemStartRequests` entry. A live manual throw (log 05-24) before `UsingSpell` shows `QRY_GetMoveForbiddenItemInfo` and `AddedTo(item, caster, "Regular")`: the engine itself lifts the item into hand as part of the client flow — the synthetic request lacks this step. The research verdict "throw cannot be automated" was confirmed. Possible future return paths: a client-initiated flow (Ecl-initiated Throw from the inventory), `AnubisPickUpItem`/`AnubisMoveItem` before the `ItemStartRequests`, capturing a live snapshot of the queue during a manual throw, initializing `ActionOriginator`/`StoryActionId`. Details and the bench list: `.scratch/bg3-neuro-followups/issues/28-throw-hide-combat-actions.md`.
